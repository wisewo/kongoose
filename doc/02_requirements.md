# Functional and Non-Functional Requirements

## Priority Rule

1. 과제 안내서의 요구사항은 반드시 만족해야 하는 상위 조건으로 본다.
2. 회의록은 팀이 정한 게임 콘셉트와 세부 기능으로 본다.
3. 과제 안내서와 회의록이 충돌하면 과제 안내서를 우선한다.
4. 회의록에 있지만 과제 요구보다 과한 기능은 선택 기능 또는 보류 기능으로 분리한다.
5. 자료에 없는 기능은 임의로 추가하지 않고 필요한 경우 `추정`으로 표시한다.

## Conflict and Scope Notes

| 구분 | 내용 | 처리 |
|---|---|---|
| 충돌 | 회의록에는 스테이지 클리어 후 바로 다음 스테이지로 이동한다고 되어 있으나, 과제 안내서는 종료/결과 화면 전환을 요구한다. | 과제 안내서 우선. 스테이지 클리어 후 결과 화면을 표시하고 플레이어가 다음 행동을 선택한다. |
| 비충돌 | 과제 안내서의 점수·시간·라이프 등 상태 표시와 회의록의 목숨 개념 없음 | 라이프는 사용하지 않고 현재 스테이지, 경과 시간, 별점 정보를 표시한다. |
| 결정 | 플레이어 이동 직후 판정과 게임 루프 갱신 판정의 책임 | `Stage`가 같은 판정 규칙을 이동 직후와 `update(dt)` 직후에 모두 적용한다. |
| 결정 | 강 칸 진입 가능 여부 | `TerrainMap.can_enter()`는 강 칸을 막지 않는다. 강에 자라가 없거나 자라에 탄 채 화면 밖으로 밀려나는 실패는 `Stage`가 판정한다. |
| 결정 | 2.5D 표현 방식 | 첫 구현의 2.5D는 얕은 등각 투영 방식으로 처리한다. 게임 로직은 2D 격자 좌표를 유지하고, `PlayingScene`이 렌더링할 때만 row/column 좌표를 대각선 화면 좌표로 변환한다. |
| 선택/보류 | 방패 아이템, 커스터마이징, 헤엄 기능, 비주기적 거위 울음소리, 즉시 실패 처리 | 필수 요구사항에서 제외한다. |
| 추정 | 저장 파일 형식 | 구체 형식은 자료에 없으므로 구현 단계에서 결정한다. |

| ID | Requirement | Source | Priority | Related Use Case |
|---|---|---|---|---|
| NFR-01 | 게임은 Python 3.10+ 환경에서 실행 가능해야 한다. | 과제 안내서 | Must | UC-01 |
| NFR-02 | GUI 라이브러리는 Pygame으로 확정한다. | 결정사항 | Must | UC-01 |
| NFR-03 | 코드는 함수, 클래스, 모듈 구조를 활용하여 500~1,500줄 규모에 적합한 구조로 작성되어야 한다. | 과제 안내서 | Must | 전체 |
| NFR-04 | 코드는 가독성과 유지보수성을 고려하여 작성되어야 한다. | 과제 안내서 | Must | 전체 |
| NFR-05 | 게임은 키보드 입력에 대해 즉각적인 반응을 제공해야 한다. | 과제 안내서, 회의록 | Must | UC-05 |

| NFR-07 | 저장 데이터는 게임 재실행 후에도 유지되어야 한다. | 과제 안내서, 결정사항 | Must | UC-01, UC-05 |
| NFR-08 | 스테이지별 난이도는 플레이 중 실시간으로 변하지 않고 고정되어야 한다. | 회의록 | Should | UC-05 |
| NFR-09 | 스테이지가 진행될수록 난이도가 높아지도록 장애물 속도, 배치, 발판 속도, 안전지대 간격 등을 조절해야 한다. | 회의록 | Should | UC-05 |
| NFR-10 | 러닝크루 경고음은 실제 러닝크루 등장과 연결되어야 하며, 자전거 환경음과 역할이 혼동되지 않아야 한다. | 회의록 | Should | UC-05 |
