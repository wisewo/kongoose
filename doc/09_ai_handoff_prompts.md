# AI 작업 분배 프롬프트

## 목적

이 문서는 팀원이나 다른 AI에게 구현 작업을 나눠줄 때 사용할 수 있는 작업 지시
프롬프트 모음이다. 각 프롬프트는 범위를 의도적으로 좁게 잡아, 서로 다른 작업물이
통합 단계에서 충돌하지 않도록 돕는다.

## 공통 지시문

아래 문구를 각 작업 프롬프트 앞에 붙여 사용한다.

```text
너는 Python 3.10+ / Pygame 기반 격자형 게임 프로젝트의 구현 담당자다.
이 게임은 '길건너 친구들'류의 한 칸 이동과 장애물 회피 구조를 참고하지만,
건국대 캠퍼스를 건구스가 이동하는 4개 고정 스테이지 게임으로 변형한 프로젝트다.

이 프로젝트의 팀원은 컴퓨터공학 전공자가 아니다.
설명은 초보자가 따라 할 수 있게 짧고 구체적으로 작성해라.
어려운 용어를 쓰면 바로 옆에 쉬운 뜻을 함께 적어라.
파일을 만들거나 수정했다면 "어떤 파일을 왜 바꿨는지"를 쉬운 말로 설명해라.

반드시 먼저 다음 문서를 읽고, 문서와 충돌하는 동작을 임의로 추가하지 마라.

1. doc/02_requirements.md
2. doc/06_class_diagram.md
3. doc/05_sequence_diagrams.md
4. doc/07_stage_balance.md
5. doc/10_team_workflow.md

담당 범위 밖의 기능은 직접 구현하지 말고, 필요한 인터페이스나 가정만 명시해라.

구현 후에는 다음 내용을 반드시 보고해라.

1. 변경 파일
2. 추가하거나 수정한 단위 테스트
3. 실행한 검증 명령과 결과
4. 수동 확인 방법과 결과
5. 남은 이슈

화면 없이 검증 가능한 로직을 바꿨다면 반드시 단위 테스트를 작성해라. 단위 테스트를 작성하지
못했다면 그 이유와 대신 수행한 수동 검증을 명시해라.
```

## 초보 팀원용 추가 문장

팀원이 AI에게 작업을 맡길 때는 공통 지시문 뒤에 아래와 같은 문장을 덧붙이면 좋다.

```text
나는 Git, pytest, ruff, Pygame 프로젝트 구조가 아직 익숙하지 않다.
내가 그대로 따라 할 수 있도록 작업 순서와 실행 명령을 단계별로 알려줘.
코드를 만든 뒤에는 내가 무엇을 확인해야 하는지도 체크리스트로 알려줘.
```

## PR/CI 공통 규칙

팀 작업은 PR 기반으로 진행한다. `main` 브랜치에는 직접 병합하지 않고, CI 통과와
팀원 1명 승인을 받은 뒤 병합한다.

AI에게 구현을 요청할 때는 아래 규칙을 반드시 포함한다.

```text
이 작업은 PR로 main에 병합될 코드다.
코드는 팀원이 리뷰할 수 있도록 작고 명확하게 작성해라.
설계 문서와 충돌하는 기능을 임의로 추가하지 마라.
초보 팀원이 읽어도 이해할 수 있도록 변경 이유를 쉽게 설명해라.

검증 가능한 로직을 변경했다면 pytest 단위 테스트를 반드시 함께 작성해라.
테스트 대상 예시는 Position, TerrainMap, Stage 이동/판정, Progress, SaveManager,
StarRating 같은 화면 없이 검증 가능한 코드다.

Pygame 화면, 사운드, 키보드 조작감처럼 자동 테스트가 어려운 부분은 수동 검증 방법과
확인 결과를 보고해라.

작업 완료 전 아래 명령을 실행할 수 있는 구조라면 실행하고 결과를 보고해라.

python -m pytest
python -m ruff check .
python -m ruff format --check .
```

검증 명령을 실행할 수 없었다면 "실행하지 못함"이라고 적고 이유를 설명한다. 실패했다면
실패 로그를 숨기지 말고, 다음에 확인해야 할 파일이나 명령을 함께 적는다.

## AI 결과 검토 체크리스트

AI가 만든 코드를 받은 팀원은 PR을 올리기 전에 아래 항목을 확인한다.

| 확인 항목 | 기준 |
|---|---|
| 문서 준수 | `doc/02`, `doc/05`, `doc/06`, `doc/07`, `doc/10`과 충돌하지 않는다. |
| 담당 범위 | 요청한 작업 패키지 밖의 기능을 임의로 구현하지 않았다. |
| 테스트 | 화면 없이 검증 가능한 로직에는 단위 테스트가 있다. |
| 수동 검증 | Pygame 실행, 화면 전환, 사운드 등은 수동 확인 결과가 있다. |
| 명명 규칙 | 클래스는 CapWords, 함수/변수는 snake_case, 상수/enum은 UPPER_CASE를 따른다. |
| 설명 가능성 | 팀원이 주요 변경 내용을 자신의 말로 설명할 수 있다. |
| PR 준비 | 변경 파일, 검증 명령, 남은 이슈를 PR 설명에 적을 수 있다. |

어떤 항목을 확인해야 할지 모르겠다면 AI에게 아래처럼 다시 묻는다.

```text
아래 변경 내용을 PR로 올리기 전에 확인해야 해.
문서와 충돌하는 부분, 테스트가 필요한 부분,
PR 설명에 적어야 할 내용을 쉽게 정리해줘.
```

## CORE: 공통 골격과 계약

```text
담당 범위는 프로젝트 공통 골격이다.

구현 대상:
- 실행 진입점
- Game 클래스의 기본 구조
- Scene 인터페이스 또는 추상 기반
- 공통 enum/result 객체
- 최소한의 Pygame 초기화와 메인 루프

주의:
- 구체적인 화면 UI, 장애물 판정, 저장/사운드 세부 구현은 담당하지 않는다.
- SceneManager는 만들지 말고 Game.change_scene(scene) 형태를 따른다.
- 다른 담당자가 이어 붙일 수 있도록 메서드 이름과 반환 타입을 명확히 유지한다.

완료 기준:
- 게임을 실행하면 Pygame 창이 열린다.
- 임시 Scene 하나를 Game이 보관하고 update/draw를 호출할 수 있다.
- 다른 작업자가 Scene, Stage, Progress 구현을 연결할 수 있는 골격이 있다.
- 공통 enum/result 객체는 간단한 단위 테스트로 생성과 상태 판정을 확인할 수 있다.
```

## A: 화면과 Scene

```text
담당 범위는 화면 상태와 Scene 계층이다.

구현 대상:
- MainScene
- StageSelectScene
- PlayingScene
- FailedScene
- ResultScene
- 각 Scene의 enter(game), handle_event(event), update(dt), draw(surface)

주의:
- Stage 내부 판정, 저장, 사운드 로직을 직접 구현하지 않는다.
- 버튼이나 키 입력은 Game의 시스템 오퍼레이션으로 연결한다.
- 화면은 우선 단순 도형과 텍스트로 구현해도 된다.

완료 기준:
- 메인 화면에서 스테이지 선택 화면으로 이동할 수 있다.
- 스테이지 선택, 실패, 결과 화면의 기본 이동 버튼이 동작한다.
- PlayingScene이 현재 스테이지, 경과 시간 등 상태 정보를 표시할 수 있다.
- 화면 전환은 수동 검증 결과를 기록한다.
```

## B: 지형과 플레이어 이동

```text
담당 범위는 정적 지형과 플레이어의 한 칸 이동이다.

구현 대상:
- Position
- TerrainType
- TerrainMap
- Player
- Stage.move_player(direction)
- 4개 고정 스테이지의 기본 맵 데이터 초안

주의:
- TerrainMap.can_enter(position)은 맵 범위와 벽 같은 정적 진입 불가 지형만 판단한다.
- 호수 칸은 can_enter에서 막지 않는다.
- 자전거, 러닝크루, 자라 판정은 C 담당 범위다.
- 결과는 MoveResult 형태로 반환한다.

완료 기준:
- 방향키 방향에 따라 목표 Position이 계산된다.
- 벽과 맵 밖 이동은 막힌다.
- 이동 가능한 칸이면 Player 위치가 갱신된다.
- START에서 GOAL까지 이동 가능한 고정 맵 초안이 있다.
- Position, TerrainMap, Stage.move_player()의 주요 판정은 단위 테스트로 확인한다.
```

## C: 장애물, 호수, 자라 판정

```text
담당 범위는 동적 객체와 스테이지 판정이다.

구현 대상:
- GameSprite
- Bike
- RunningCrew
- Turtle
- Stage.update(dt)
- Stage.evaluate_player_state()
- StageUpdateResult

주의:
- 플레이어 이동 직후와 동적 객체 갱신 직후 모두 같은 evaluate_player_state() 규칙을 사용한다.
- 목적지는 별도 Goal 클래스가 아니라 TerrainType.GOAL로 판단한다.
- 저장, 별점, 화면 전환 자체는 담당하지 않고 결과 객체로 상태를 전달한다.

완료 기준:
- 자전거 또는 러닝크루와 충돌하면 실패 결과가 반환된다.
- 자라 없이 호수 위에 있으면 실패 결과가 반환된다.
- 자라 위에 있으면 플레이어가 자라 이동을 따라간다.
- 자라에 탄 채 화면 밖으로 밀려나면 실패 결과가 반환된다.
- 충돌, 호수 추락, 자라 탑승, 화면 밖 밀림은 단위 테스트로 확인한다.
```

## D: 진행 상태, 저장, 별점, 리소스

```text
담당 범위는 진행 상태와 보조 매니저이다.

구현 대상:
- Progress
- SaveManager
- Timer
- StarRating
- SoundManager
- SoundCue
- ResourceManager

주의:
- Progress는 스테이지 해금과 최고 별점 규칙을 담당한다.
- SaveManager는 파일 저장/불러오기만 담당한다.
- SoundManager는 SoundCue를 받아 play(cue) 형태로 재생한다.
- 이미지 리소스가 없으면 ResourceManager는 도형 대체가 가능하도록 실패를 안전하게 처리한다.

완료 기준:
- 스테이지 클리어 시 다음 스테이지 해금과 최고 별점 갱신이 가능하다.
- 저장 파일을 통해 재실행 후 진행 상태가 유지된다.
- 클리어 시간으로 1~3성 별점을 계산할 수 있다.
- 최소 1종 이상의 사운드를 로드하거나 대체 처리할 수 있다.
- Progress, SaveManager, StarRating은 단위 테스트로 확인한다.
- 사운드와 이미지 리소스는 없을 때도 안전하게 처리되는지 확인한다.
```

## INT: 통합과 수동 검증

```text
담당 범위는 구현된 모듈을 합쳐 실제 플레이 가능한 상태로 만드는 것이다.

구현 대상:
- Game과 Scene, Stage, Progress, SoundManager 연결
- 4개 스테이지 플레이 흐름 연결
- 수동 검증 체크리스트 수행
- 발견한 버그 수정 또는 이슈 기록

주의:
- 설계와 다르게 동작하는 부분은 먼저 문서 기준과 비교해 설명한다.
- 난이도 조정은 doc/07_stage_balance.md의 조정 규칙을 따른다.
- 큰 구조 변경보다 작은 수정으로 통합 안정성을 우선한다.

완료 기준:
- 메인 화면에서 시작해 4개 스테이지를 순서대로 진행할 수 있다.
- 실패, 재시작, 스테이지 선택, 결과 화면 이동이 동작한다.
- 해금 상태와 최고 별점이 저장된다.
- 사람이 직접 플레이한 검증 결과가 기록되어 있다.
- pytest와 ruff 검증이 통과한다.
```
