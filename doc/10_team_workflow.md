# 팀 작업 안내서

## 이 문서는 왜 있나요?

우리 팀은 5명이 함께 게임을 만든다. 모두 AI를 사용할 수 있지만, Git이나 테스트가
익숙하지 않을 수 있다. 그래서 이 문서는 "외워야 하는 규칙"이 아니라 "그대로 따라 하면
되는 순서"를 적어둔 안내서다.

막히면 혼자 오래 붙잡지 말고 팀장이나 AI에게 물어본다. 모르는 상태에서 억지로
진행하는 것보다 빨리 물어보는 것이 더 좋은 협업이다.

## 꼭 기억할 것 3가지

1. `main` 브랜치에는 직접 코드를 올리지 않는다.
2. 내 작업은 Pull Request(PR)로 올리고, 팀원 1명이 확인한 뒤 합친다.
3. AI가 만든 코드도 내가 실행해보고, 설명할 수 있어야 한다.

## 용어 짧게 설명

| 용어 | 뜻 |
|---|---|
| `main` | 모두가 공유하는 최종 코드 줄기. 항상 실행 가능한 상태로 유지한다. |
| 브랜치 | 내 작업을 따로 해보는 공간. 연습장처럼 생각하면 된다. |
| PR | "제가 이렇게 바꿨는데 확인해주세요"라고 올리는 요청이다. |
| CI | GitHub가 자동으로 테스트와 코드 검사를 돌려주는 장치다. |
| 리뷰 | 팀원이 내 코드를 보고 이상한 점이 없는지 확인해주는 과정이다. |
| 단위 테스트 | 작은 기능 하나가 맞게 동작하는지 확인하는 코드다. |
| 수동 검증 | 사람이 직접 게임을 실행해서 확인하는 것이다. |

## 작업 순서

### 1. 내 담당 범위 확인하기

먼저 내가 맡은 작업이 무엇인지 확인한다. 작업 범위는 `doc/08_implementation_dashboard.md`
와 `doc/09_ai_handoff_prompts.md`에 적혀 있다.

예를 들어 `B: 지형과 플레이어 이동`을 맡았다면 화면이나 사운드까지 만들려고 하지 말고,
지형과 이동만 집중한다.

### 2. 새 브랜치 만들기

작업할 때는 새 브랜치를 만든다. 브랜치 이름은 너무 고민하지 말고 아래처럼 만든다.

```powershell
git checkout -b feature/stage-movement
```

예시:

- `feature/core-game-loop`
- `feature/stage-movement`
- `feature/scene-flow`
- `feature/save-progress`
- `docs/team-guide`

### 3. AI에게 물어볼 때는 프롬프트를 같이 주기

AI에게 바로 "이거 만들어줘"라고만 말하면 범위를 넘거나 이상한 코드를 만들 수 있다.
반드시 `doc/09_ai_handoff_prompts.md`에서 내 담당 범위에 맞는 프롬프트를 복사해서 같이
넣는다.

AI에게 이렇게 추가로 말하면 좋다.

```text
나는 컴퓨터공학 전공자가 아니라서 Git, 테스트, Python 구조가 아직 익숙하지 않아.
코드를 만들 때 파일별로 어디를 바꾸는지 쉽게 설명해줘.
내가 실행해야 할 명령도 순서대로 알려줘.
```

### 4. 코드를 만든 뒤 확인하기

AI가 코드를 만들어도 바로 PR을 올리지 않는다. 먼저 내가 확인한다.

확인할 것은 세 가지다.

1. 게임이나 테스트가 실행되는가
2. 내가 맡은 범위만 바꿨는가
3. PR 설명에 적을 만큼 변경 내용을 이해했는가

테스트와 코드 검사는 아래 명령으로 한다. 아직 CI 설정 전이거나 명령이 실패하면, 실패
내용을 PR에 적고 팀장에게 물어본다.

```powershell
python -m pytest
python -m ruff check .
python -m ruff format --check .
```

게임 실행 명령은 구현 구조가 확정되면 README에 맞춰 갱신한다. 기준 명령은 다음과 같다.

```powershell
python -m kongoose
```

### 5. PR 올리기

PR에는 아래 내용을 짧게 적는다.

```text
## 작업 내용
-

## 읽은 문서
- doc/02_requirements.md
- doc/06_class_diagram.md
- doc/05_sequence_diagrams.md
- doc/07_stage_balance.md
- doc/10_team_workflow.md

## 테스트
- [ ] python -m pytest
- [ ] python -m ruff check .
- [ ] python -m ruff format --check .

## 수동 확인
-

## 남은 문제
-
```

모든 항목을 완벽하게 채우지 못해도 괜찮다. 대신 비워두지 말고 "아직 못 했다",
"무엇을 해야 할지 모르겠다"처럼 현재 상태를 적는다.

### 6. 리뷰 받기

PR은 팀원 1명이 승인해야 `main`에 합칠 수 있다. 리뷰를 받는 것은 지적받는 과정이
아니라, 실수를 같이 줄이는 과정이다.

리뷰어가 질문하거나 수정을 요청하면 다음 중 하나로 답한다.

- "수정했습니다. 다시 확인해주세요."
- "이 부분은 잘 모르겠어서 팀장/AI에게 확인해보겠습니다."
- "문서와 다르게 구현한 것 같아서 다시 고치겠습니다."

## 언제 단위 테스트를 써야 하나요?

화면을 보지 않아도 답이 정해지는 기능은 테스트를 쓰는 것이 좋다.

테스트를 써야 하는 예:

- 방향키를 누르면 위치가 한 칸 바뀌는지
- 벽이나 맵 밖으로 이동하지 못하는지
- 목적지에 도착하면 클리어가 되는지
- 자전거와 부딪히면 실패가 되는지
- 스테이지를 클리어하면 다음 스테이지가 열리는지
- 클리어 시간에 따라 별점이 맞게 나오는지
- 저장한 진행 상태를 다시 불러올 수 있는지

사람이 직접 확인해도 되는 예:

- Pygame 창이 실제로 열리는지
- 화면 전환이 자연스러운지
- 키보드 조작감이 괜찮은지
- 사운드가 들리는지
- 스테이지가 너무 어렵거나 쉽지 않은지

테스트를 못 쓰겠으면 AI에게 이렇게 물어본다.

```text
아래 코드는 화면 없이 검증 가능한 로직이야.
pytest로 가장 기본적인 단위 테스트를 만들어줘.
나는 테스트가 익숙하지 않으니, tests 폴더에 어떤 파일을 만들고
어떤 명령으로 실행해야 하는지도 알려줘.
```

## 리뷰어는 무엇을 보면 되나요?

리뷰어도 모든 코드를 완벽히 이해할 필요는 없다. 아래만 확인해도 충분하다.

1. PR 설명이 비어 있지 않은가
2. 담당 범위 밖의 기능을 갑자기 만들지 않았는가
3. 테스트나 수동 확인 기록이 있는가
4. 실행 명령이 적혀 있는가
5. 코드가 너무 이해하기 어렵다면 작성자에게 설명을 요청했는가

이해가 안 되면 이렇게 물어본다.

```text
이 PR을 리뷰해야 하는데 내가 초보라서 어렵다.
변경된 파일을 기준으로 위험해 보이는 부분과 작성자에게 물어볼 질문을 쉽게 정리해줘.
```

## 막혔을 때 바로 쓰는 질문

Git에서 막혔을 때:

```text
내가 지금 Git 작업 중인데 무엇을 해야 할지 모르겠어.
현재 상황을 확인하는 명령부터 알려주고, 위험한 명령은 쓰기 전에 경고해줘.
```

테스트가 실패했을 때:

```text
pytest가 실패했어. 아래 에러를 보고 원인을 쉽게 설명해줘.
바로 코드를 고치기 전에 어떤 파일을 확인해야 하는지도 알려줘.
```

CI가 실패했을 때:

```text
GitHub Actions CI가 실패했어.
아래 로그를 보고 내가 해야 할 일을 순서대로 알려줘.
```

PR 설명을 쓰기 어려울 때:

```text
아래 변경 내용을 보고 PR 설명을 초보자도 이해하기 쉽게 작성해줘.
작업 내용, 테스트, 수동 확인, 남은 문제로 나눠줘.
```

## 마지막 확인

PR을 올리기 전에 아래 질문에 답해본다.

- 내가 어떤 파일을 왜 바꿨는지 한 문장으로 말할 수 있는가?
- 테스트나 수동 확인 중 하나 이상을 했는가?
- AI가 만든 코드 중 이해가 안 되는 부분을 그대로 두지 않았는가?
- 팀원이 리뷰할 수 있게 PR 설명을 적었는가?

네 개 중 하나라도 어렵다면 괜찮다. 그 부분을 PR에 적거나 팀장/AI에게 물어보면 된다.
